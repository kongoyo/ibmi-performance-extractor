# 多日趨勢與容量規劃報告

**主機**：clark75 (172.16.12.126) ／ Library：QPFRDATA
**日期區間**：08/05 ～ 08/07（共 3 天）

---

## 一、結論先講：**建議評估擴充資源**

CPU 使用率與 Page Faults 這兩項有門檻的關鍵指標，在觀測區間的最後一天（08/07）**雙雙已超標**，而且都呈現快速上升趨勢，並非單日偶發尖峰。Response Time 目前仍安全，是唯一的緩衝空間，但若 CPU/Memory 壓力持續惡化，回應時間隨時可能被拖垮。建議儘快排查 08/07 17:00 前後的工作負載，並評估是否需要增加 CPU 或記憶體資源。

---

## 二、逐項指標分析

### Total CPU — ⚠️ 已超標，且快速惡化

| 日期 | 當日峰值 | 發生時間 |
| :--- | ---: | :--- |
| 08/05 | 11% | 10:15 |
| 08/06 | 45% | 11:30 |
| 08/07 | **94%** | 17:00 |

- 每日成長斜率：+41.5%/天；三天內從 11% 飆升至 94%，首末差值 +83%。
- 08/07 已超過警戒門檻（70%），且是三天中唯一超標的一天——不是持續性問題，而是**剛開始惡化**。
- 進一步拆解可看到 Batch CPU（批次）與 Total CPU 走勢完全一致（08/07 同為 94%），代表 08/07 17:00 的 CPU 飆升主要來自批次工作負載，而非互動式工作（Interactive CPU 08/07 僅 22%）。若要追查是哪個 Job 造成，建議對 clark75 08/07 17:00 執行 `npm run anomaly` 找出當時的異常 Job。

### Page Faults（分頁缺失）— ⚠️ 已超標，且加速惡化

| 日期 | 當日峰值 | 發生時間 |
| :--- | ---: | :--- |
| 08/05 | 60 | 10:15 |
| 08/06 | 462 | 14:30 |
| 08/07 | **557** | 17:00 |

- 每日成長斜率：+248.5/天，遠超過門檻（50），且三天皆超標，惡化速度比 CPU 更早開始、更持續。
- Page Faults 與 CPU 峰值同樣落在 08/07 17:00 附近，兩者高度相關，指向記憶體集區（memory pool）在該批次工作負載下容量吃緊，導致頻繁換頁，進而推高 CPU 負擔。

### Response Time（回應時間）— 目前安全，但非決定性訊號

| 日期 | 當日峰值 | 發生時間 |
| :--- | ---: | :--- |
| 08/05 | 1.02 秒 | 10:30 |
| 08/06 | 4.63 秒 | 17:45 |
| 08/07 | 0.46 秒 | 17:15 |

- 三天皆未超過 2.0 秒門檻，且整體斜率為負（-0.28 秒/天），08/07 反而是三天中最低點。
- 這代表目前的 CPU/Page Faults 壓力**尚未**傳導到終端使用者的回應時間上，但這通常只是時間差——批次工作與互動式工作分屬不同資源池，若批次工作持續吃資源，一旦互動式工作也開始排擠，回應時間可能在後續幾天才會明顯反映。不宜以此判斷「系統沒問題」。

### Transaction Count / Interactive CPU / Disk I/O — 觀察中，非急迫項

- 交易量三天內成長近 10 倍（138 → 1361），但無門檻可比，且與 CPU/Page Faults 走勢相符，較可能是業務量本身成長（例如批次作業規模擴大），而非異常。
- Disk I/O 峰值偏低（最高 22，無門檻），三天內無明顯瓶頸跡象。

---

## 三、建議

1. **優先排查 08/07 17:00 前後的批次工作**：CPU 與 Page Faults 的峰值都集中在同一時段，建議針對 clark75 08/07 17:00 執行 `npm run anomaly -- --host=<HostID> --lib=QPFRDATA --date=08/07`，找出當時佔用資源最多的 Job，確認是否為預期中的批次作業規模成長，或是異常程式（例如迴圈、鎖等待）。
2. **持續觀察 1-2 天**：目前僅 3 天資料、且超標只發生在最後一天，樣本仍偏薄，建議延長觀測區間（例如再擷取 08/08～08/10）以確認是持續惡化還是單次尖峰。
3. **若確認為業務量成長導致**，且斜率持續（CPU +41.5%/天、Page Faults +248.5/天），以目前速度推算，CPU 有可能在 1～2 天內逼近滿載，屆時應考慮擴充 CPU 或記憶體資源，或評估將該批次作業排程分散到離峰時段。
